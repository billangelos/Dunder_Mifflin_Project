# 1. Purpose

This register provides centralized document-control information for controlled artifacts within the Dunder Mifflin Enterprise Information Security & Risk Management Program.

The register supports:

- Artifact identification
- Repository location
- Version control
- Classification
- Status tracking
- Ownership
- Approval accountability
- Review requirements

This register does not replace the document-control information contained within individual artifacts.

---

# 2. Document Control Principles

Controlled artifacts must:

- Have a unique artifact identifier.
- Have a defined title.
- Have a version.
- Have a classification.
- Have a status.
- Have an identified owner.
- Identify approval authority where applicable.
- Have an effective date where applicable.
- Have a defined review frequency where applicable.
- Maintain revision history appropriate to the artifact.

Artifact identifiers remain associated with the artifact even if repository location changes.

---

# 3. Status Definitions

## Approved

The artifact has completed its initial development and approval process.

## Active

The artifact is a living register, index, matrix, catalog, dashboard, or other operational record that is maintained as program information changes.

## Planned

The artifact has been identified as part of the security program but has not yet been completed and approved.

## Draft

The artifact is under development and has not received final approval.

## Retired

The artifact is no longer active but is retained when required for historical, legal, operational, or evidentiary purposes.

---

# 4. Versioning

Version numbers use the following general convention:

- **0.x** - Draft development
- **1.0** - Initial approved version
- **1.x** - Minor approved revision
- **2.0** - Significant revision

Version numbers must reflect actual document history.

Version history must not be manufactured solely to make an artifact appear more mature.

---

# 5. Classification

Repository artifacts must be classified according to:

- [[POL-004 Information Classification & Handling Policy]]
- [[STD-001 Information Classification Standard]]

Common document classifications include:

- Public
- Internal
- Confidential
- Restricted

Classification must reflect document content.

# 22. Approval Authority

Approval authority must reflect the significance of the artifact.

General expectations are:

| Artifact Type | Typical Approval |
|---|---|
| Enterprise Program | CEO |
| Governance Framework | CEO |
| Enterprise Policy | CEO |
| Major Enterprise Plan | CEO |
| Technical Standard | CIO |
| Procedure | Responsible Executive or CIO |
| Register | Responsible Owner |
| Operational Template | Responsible Owner |
| Executive Report | Appropriate Executive Authority |

The approval model may vary when the subject matter requires different authority.

---

# 23. Ownership

Document ownership identifies accountability for maintaining the artifact.

The owner is responsible for ensuring, as applicable:

- Periodic review occurs.
- Material changes are incorporated.
- Required approvals are obtained.
- Related artifacts remain aligned.
- Obsolete content is corrected.
- Revision history is maintained.

Ownership does not mean the owner personally performs every activity described in the artifact.

---

# 24. Review Frequency

Review frequency defines the minimum expected review cycle.

Additional review must occur when triggered by significant events such as:

- Material business change
- Material technology change
- Significant security incident
- Significant control failure
- Major assessment finding
- Legal or contractual change
- Significant third-party change
- Material risk change

A scheduled review is not a substitute for event-driven review when circumstances materially change.

---

# 25. Planned Artifacts

A Planned artifact represents intended program documentation.

Planned status does not establish that:

- The artifact exists in approved form.
- Associated controls are implemented.
- Associated procedures are operational.
- Required evidence exists.
- The control is effective.

Planned controls receive no credit when determining current residual risk.

---

# 26. Approved Artifacts

Approved status indicates that an artifact has completed its initial development and approval process.

Approved documentation does not independently prove that every requirement within the artifact has been implemented or is operating effectively.

Implementation and effectiveness require appropriate evidence and validation.

---

# 27. Active Registers and Reference Records

Registers, indexes, matrices, catalogs, and operational dashboards designated Active are living records.

They must be updated when relevant program information changes.

An Active artifact may contain:

- Existing conditions
- Approved requirements
- Planned activities
- Open findings
- Historical information
- Current operational or reporting information

Status must be clear enough to distinguish these conditions.

---

# 28. Revision Control

Material document revisions must be recorded in the artifact's revision history.

Revision history should identify:

- Version
- Date
- Description
- Approval where applicable

Minor editorial corrections that do not alter requirements may be incorporated without creating unnecessary version history when document-control procedures permit.

Material changes to requirements must receive appropriate review and approval.

---

# 29. Historical Integrity

Historical records must not be rewritten solely to make earlier program conditions appear stronger than they were.

When later information identifies:

- A factual error,
- An incorrect baseline assumption,
- A scoring error, or
- Another material documentation problem,

the artifact may be corrected with appropriate traceability.

Historical security conditions and assessment results must otherwise remain distinguishable from later improvements.

---

# 30. Cross-Reference Control

Controlled artifacts should reference related artifacts using:

**Document ID + Full Artifact Title**

Obsidian links may use the complete artifact filename, for example:

`[[POL-005 Risk Management Policy]]`

Detailed program relationships are maintained in [[REG-007 Cross-Reference Matrix]].

Cross-references must be verified during repository quality assurance to prevent:

- Dead links
- Obsolete identifiers
- Incorrect titles
- Incorrect destinations
- References to retired temporary artifact names

---

# 31. Repository Location

Repository location is organizational rather than authoritative identity.

Moving an artifact between folders does not require changing its artifact identifier solely because its location changed.

Artifact identifiers must remain stable unless a legitimate document-control reason requires replacement.

---

# 32. Artifact Creation

Before a new controlled artifact is added, the artifact should have:

- Defined purpose
- Appropriate artifact type
- Unique identifier
- Defined owner
- Appropriate classification
- Expected approval authority
- Repository location

The artifact must then be added to:

- [[INDEX-001 Artifact Index]]
- This document-control register
- [[REG-007 Cross-Reference Matrix]] where applicable

---

# 33. Artifact Retirement

Retired artifacts must be clearly identified.

Retirement should consider:

- Replacement artifact
- Historical need
- Legal retention
- Audit evidence
- Existing references
- Repository navigation

Retired artifacts must not remain presented as current requirements.

---

# 34. Document Quality Assurance

Repository quality assurance must periodically verify:

- Artifact identifiers
- Titles
- Locations
- Versions
- Status
- Ownership
- Approval
- Review frequency
- Cross-references
- Terminology
- Revision history

Quality assurance must distinguish editorial cleanup from substantive requirement changes.

---

# 35. Relationship to Risk Management

Document control supports risk management by preserving traceability between:

**Risk → Treatment → Policy / Standard → Control → Procedure → Implementation → Evidence → Assessment → Finding → Remediation → Retest → Risk Reassessment**

Poor document control can weaken assurance even when technical controls exist because requirements and evidence may no longer be reliably connected.

---

# 36. Evidence Integrity

Document-control records must reflect actual program conditions.

Personnel must not:

- Invent approval dates.
- Create false revision history.
- Mark unfinished artifacts Approved.
- Represent Planned controls as implemented.
- Backdate documents to create false evidence.
- Conceal superseded requirements.
- Alter historical assessment results without traceability.

Documentation integrity is part of security assurance.

---

# 37. Maintenance

This register must be updated when:

- A controlled artifact is created.
- An artifact becomes Approved.
- An artifact status changes.
- A version changes.
- Ownership changes.
- Approval authority changes.
- Repository location changes.
- An artifact is retired.
- A material document-control error is identified.
